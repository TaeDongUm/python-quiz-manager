# 기능 단위 체크리스트

## 1. 프로그램 실행 및 메뉴

- [x] 프로그램을 실행하면 퀴즈 풀기, 퀴즈 추가, 퀴즈 목록, 점수 확인, 종료 메뉴가 출력된다.
- [x] 사용자가 메뉴 번호를 입력하면 선택한 기능이 실행된다.
- [x] 기능 실행이 끝나면 다시 메인 메뉴로 돌아간다.
- [x] 종료 메뉴를 선택하면 프로그램이 정상적으로 종료된다.

## 2. 입력 및 예외 처리

- [x] 입력값의 앞뒤 공백을 제거한 후 처리한다.
- [x] 빈 값, 문자가 포함된 값, 허용 범위를 벗어난 숫자를 입력하면 안내 메시지를 출력하고 다시 입력받는다.
- [x] 메뉴 번호와 퀴즈 정답 번호의 입력 범위를 각각 검사한다.
- [x] 실행 중 `Ctrl+C` 또는 입력 스트림 종료가 발생하면 가능한 데이터를 저장하고 안전하게 종료한다. (데이터 저장 로직 구현 x)
- [x] 데이터 파일이 없거나 손상되어도 프로그램을 실행할 수 있다. (초기화 데이터는 아직 구현 x)

## 3. 기본 퀴즈 제공

- [x] 직접 선택한 하나의 주제로 기본 퀴즈를 5개 이상 제공한다. (Python 기초 문제 작성)
- [x] 각 퀴즈는 문제, 선택지 4개, 정답 번호를 포함한다.
- [x] 저장된 데이터가 없는 첫 실행에서는 기본 퀴즈를 불러온다.

## 4. 퀴즈 풀기

- [x] 저장된 퀴즈의 문제와 선택지 4개를 사용자에게 순서대로 출력한다.
- [x] 사용자가 1~4 사이의 정답 번호를 입력할 수 있다.
- [x] 정답 입력 후 정답 또는 오답 여부를 알려준다.
- [x] 모든 퀴즈를 풀면 맞힌 문제 수와 최종 점수를 출력한다.
- [x] 등록된 퀴즈가 없는 경우 안내 메시지를 출력한다.
- [x] 퀴즈 풀기 기능은 별도의 Git 브랜치에서 개발한 후 `main` 브랜치에 병합한다.

## 5. 퀴즈 추가

- [x] 사용자가 새로운 문제와 선택지 4개를 입력할 수 있다.
- [x] 사용자가 1~4 사이의 정답 번호를 입력할 수 있다.
- [x] 문제, 선택지 또는 정답 번호가 잘못 입력되면 안내 후 다시 입력받는다. (빈 입력에 대한 검증 로직만 추가)
- [x] 입력한 내용으로 새로운 퀴즈를 생성하여 기존 퀴즈 목록에 추가한다.
- [x] 추가한 퀴즈를 즉시 데이터 파일에 저장한다.

## 6. 퀴즈 목록 확인

- [x] 현재 등록된 퀴즈의 전체 개수를 확인할 수 있다.
- [x] 등록된 퀴즈의 번호와 문제 내용을 목록으로 확인할 수 있다.
- [x] 등록된 퀴즈가 없는 경우 안내 메시지를 출력한다.
- [x] 사용자가 추가한 퀴즈도 목록에 함께 출력된다.

## 7. 점수 기록 및 확인

- [x] 퀴즈를 완료하면 획득한 점수를 계산한다.
- [x] 획득한 점수가 기존 최고 점수보다 높으면 최고 점수를 갱신한다.
- [x] 점수 확인 메뉴에서 저장된 최고 점수를 확인할 수 있다.
- [x] 아직 퀴즈를 풀지 않은 경우 안내 메시지를 출력한다.
- [x] 프로그램을 종료하고 다시 실행해도 최고 점수가 유지된다.

## 8. 데이터 저장 및 불러오기

- [x] 퀴즈 목록과 최고 점수를 프로젝트 루트의 `state.json`에 저장한다.
- [x] `state.json`을 UTF-8 인코딩으로 읽고 저장한다.
- [x] 프로그램을 다시 실행하면 이전에 추가한 퀴즈와 최고 점수를 불러온다.
- [x] `state.json`이 없는 경우 기본 퀴즈 데이터로 시작한다.
- [x] `state.json`이 손상된 경우 안내 메시지를 출력하고 기본 데이터로 복구하거나 초기화한다.
- [x] 파일 읽기 또는 쓰기 오류가 발생해도 프로그램이 비정상적으로 종료되지 않는다.

# 1. 프로그램 개요

> Python의 기본 문법과 객체지향 프로그래밍을 활용하여 사용자가 직접 퀴즈를 풀고 관리할 수 있는 콘솔 프로그램을 구현했습니다.

사용자는 다음 기능을 사용할 수 있습니다.

1. 퀴즈 풀기
2. 퀴즈 추가
3. 등록된 퀴즈 목록 확인
4. 퀴즈 삭제
5. 최고 점수 확인
6. 과거 게임 기록 확인

프로그램의 퀴즈와 점수 데이터는 프로젝트 루트의 `state.json` 파일에 저장하여 프로그램을 종료한 뒤 다시 실행해도 이전 상태가 유지되도록 구현했습니다.

또한, 객체를 설계하고 적절하게 역할을 부여하도록 설계했습니다.

`Quiz`: 하나의 퀴즈 데이터와 정답 판정

`QuizGame`: 게임 전체 진행 흐름

`ConsoleIO`: 콘솔 입출력과 입력값 검증

`QuizRepository`: 퀴즈 목록 관리

`ScoreManager`: 점수 계산 및 게임 기록 관리

`JsonStateStore`: JSON 파일 저장 및 불러오기

이를 통해 특정 기능이 변경되었을 때 수정 범위를 줄이는 것을 목표로 했습니다.

# 5. 주요 기능

### 퀴즈 풀기

등록되어 있는 퀴즈 중 사용자가 원하는 문제 수를 선택하여 풀 수 있습니다.

문제의 출제 순서는 무작위로 섞이며 각 문제마다 1~4 사이의 정답 번호를 입력합니다.

퀴즈가 끝나면 다음 내용을 확인할 수 있습니다.

- 푼 문제 수
- 맞힌 문제 수
- 최종 점수
- 최고 점수 갱신 여부

### 랜덤 출제

퀴즈를 시작할 때 전체 퀴즈 목록을 복사한 뒤 무작위로 섞어 문제를 출제합니다.

따라서 프로그램을 실행할 때마다 문제의 출제 순서가 달라질 수 있습니다.

### 문제 수 선택

퀴즈를 시작하기 전에 현재 등록된 문제 중 몇 문제를 풀 것인지 선택할 수 있습니다.

선택한 문제 수만큼 무작위로 문제를 출제합니다.

### 힌트 기능

각 `Quiz` 객체는 선택적으로 힌트를 가질 수 있습니다.

문제를 푸는 도중 힌트를 확인할 수 있으며, 힌트를 사용하면 최종 점수에서 힌트 하나당 10점이 차감됩니다.

최종 점수는 0점보다 낮아지지 않습니다.

### 퀴즈 추가

사용자가 다음 정보를 직접 입력하여 새로운 퀴즈를 추가할 수 있습니다.

- 문제
- 선택지 4개
- 정답 번호
- 힌트

추가된 퀴즈는 메모리에만 존재하는 것이 아니라 `state.json`에 저장되므로 프로그램을 다시 실행해도 유지됩니다.

### 퀴즈 목록

현재 등록되어 있는 전체 퀴즈 수와 각 퀴즈의 문제 내용을 확인할 수 있습니다.

### 퀴즈 삭제

현재 등록된 퀴즈 목록에서 번호를 선택하여 원하는 문제를 삭제할 수 있습니다.

삭제 후 변경된 퀴즈 목록을 `state.json`에 다시 저장합니다.

### 최고 점수

게임을 완료할 때마다 현재 점수를 기존 최고 점수와 비교합니다.

현재 점수가 기존 최고 점수보다 높은 경우 최고 점수를 갱신합니다.

### 게임 기록

최고 점수뿐만 아니라 각각의 게임 결과도 기록합니다.

게임 기록에는 다음 데이터가 저장됩니다.

- 게임을 진행한 날짜와 시간
- 획득한 점수
- 푼 문제 수

### 입력 검증

숫자를 입력해야 하는 곳에서는 다음과 같은 잘못된 입력을 처리합니다.

- 빈 입력
- 숫자가 아닌 문자열
- 허용 범위를 벗어난 숫자
- 입력 앞뒤의 불필요한 공백

잘못된 값을 입력하면 프로그램을 종료하지 않고 안내 메시지를 출력한 후 다시 입력받습니다.

### `main.py`

프로그램의 실행 진입점입니다.

`QuizGame` 객체를 생성하고 `run()` 메서드를 호출합니다.

프로그램 시작에 필요한 최소한의 역할만 담당합니다.

### `quiz.py`

개별 퀴즈를 표현하는 `Quiz` 클래스를 정의합니다.

주요 데이터:

- `question`
- `choices`
- `answer`
- `hint`

주요 역할:

- 퀴즈 데이터 보관
- 사용자의 정답 판정
- 객체 → `dict` 변환
- `dict` → 객체 복원
- 첫 실행에 사용할 기본 퀴즈 제공

### `quiz_game.py`

게임 전체의 진행 흐름을 관리하는 `QuizGame` 클래스를 정의합니다.

주요 역할:

- 메뉴에 따른 기능 실행
- 퀴즈 진행
- 퀴즈 추가
- 퀴즈 삭제
- 퀴즈 목록 확인
- 점수 확인
- 게임 기록 확인
- 저장소와 다른 객체들의 기능 연결

직접 모든 기능을 처리하기보다 `ConsoleIO`, `QuizRepository`, `ScoreManager`, `JsonStateStore`에 각각의 역할을 위임합니다.

### `console_io.py`

콘솔 입력과 출력 및 입력값 검증을 담당하는 `ConsoleIO` 클래스를 정의합니다.

주요 역할:

- 메뉴 출력
- 숫자 입력
- 숫자 범위 검사
- 빈 문자열 검사
- 안전 종료 메시지 출력

### `quiz_repository.py`

퀴즈 목록을 관리하는 `QuizRepository` 클래스를 정의합니다.

주요 역할:

- 퀴즈 추가
- 퀴즈 삭제
- 퀴즈 전체 조회
- 퀴즈 개수 조회
- 퀴즈 존재 여부 확인
- 랜덤 출제 순서 생성

### `score_manager.py`

점수와 게임 기록을 관리하는 `ScoreManager` 클래스를 정의합니다.

주요 역할:

- 최종 점수 계산
- 힌트 사용에 따른 점수 차감
- 최고 점수 갱신
- 게임 기록 추가
- 최고 점수 조회
- 게임 기록 조회

### `storage.py`

`state.json`을 읽고 저장하는 `JsonStateStore` 클래스를 정의합니다.

게임 로직과 파일 입출력 로직을 분리하여 JSON 파일과 관련된 처리를 담당합니다.

### `state.json`

프로그램을 종료한 뒤에도 퀴즈와 점수 정보를 유지하기 위한 데이터 파일입니다.

## 7. `state.json` 데이터 구조

프로그램의 상태 데이터는 프로젝트 루트의 다음 파일에 저장합니다.

```text
state.json
```

파일은 UTF-8 인코딩으로 읽고 쓰며 JSON 형식을 사용합니다.

현재 저장하는 최상위 데이터는 다음 세 가지입니다.

```json
{
  "quizzes": [],
  "best_score": 100,
  "score_history": []
}
```

### `quizzes`

등록된 전체 퀴즈를 배열 형태로 저장합니다.

각 퀴즈는 다음 구조를 가집니다.

```json
{
  "question": "문제 내용",
  "choices": ["선택지 1", "선택지 2", "선택지 3", "선택지 4"],
  "answer": 2,
  "hint": "힌트 내용"
}
```

필드의 의미는 다음과 같습니다.

| 필드       | 설명        |
| ---------- | ----------- |
| `question` | 퀴즈 문제   |
| `choices`  | 선택지 4개  |
| `answer`   | 정답 번호   |
| `hint`     | 문제의 힌트 |

### `best_score`

현재까지 기록한 최고 점수를 저장합니다.

아직 게임을 진행하지 않은 경우에는 값이 존재하지 않는 상태로 시작할 수 있습니다.

### `score_history`

각 게임의 결과를 배열 형태로 저장합니다.

```json
{
  "timestamp": "2026-08-09 18:21:56",
  "score": 100,
  "question_count": 3
}
```

| 필드             | 설명                      |
| ---------------- | ------------------------- |
| `timestamp`      | 게임을 진행한 날짜와 시간 |
| `score`          | 해당 게임의 최종 점수     |
| `question_count` | 해당 게임에서 푼 문제 수  |

프로그램을 실행하면 `state.json`의 데이터를 읽어 `Quiz` 객체, 최고 점수, 게임 기록으로 복원합니다.

게임 진행, 퀴즈 추가 또는 삭제 등 상태가 변경되면 현재 상태를 다시 JSON 파일에 저장합니다.

## 8. 예외 처리

프로그램이 잘못된 사용자 입력이나 파일 문제 때문에 바로 종료되지 않도록 여러 상황을 처리합니다.

### 숫자 입력 오류

숫자가 필요한 입력에서는 먼저 문자열의 앞뒤 공백을 제거합니다.

다음 입력은 잘못된 값으로 처리합니다.

```text
빈 입력
abc
허용 범위를 벗어난 숫자
```

문자열을 정수로 변환할 수 없는 경우 `ValueError`를 처리하고 다시 입력받습니다.

### `state.json`이 없는 경우

프로그램을 처음 실행했거나 `state.json`이 존재하지 않는 경우에는 `quiz.py`에 정의된 기본 퀴즈 목록을 사용합니다.

따라서 데이터 파일이 존재하지 않더라도 프로그램을 시작할 수 있습니다.

### 비어 있는 `state.json`

파일은 존재하지만 내용이 비어 있는 경우에도 기본 퀴즈 데이터를 사용합니다.

### 손상된 JSON

`state.json`의 JSON 문법이 올바르지 않아 파싱 과정에서 `JSONDecodeError`가 발생하면 오류 메시지를 출력하고 기본 퀴즈 데이터로 초기화합니다.

이를 통해 JSON 파일 하나의 손상 때문에 프로그램 전체가 실행되지 않는 상황을 방지했습니다.

### 파일 입출력 오류

파일을 읽거나 저장하는 과정에서 발생하는 `OSError`를 처리합니다.

읽기 오류가 발생하면 기본 데이터로 프로그램을 계속 실행할 수 있도록 처리하며, 저장 오류가 발생하면 오류 내용을 사용자에게 알립니다.

### `KeyboardInterrupt` / `EOFError`

프로그램 실행 중 `Ctrl+C`로 `KeyboardInterrupt`가 발생하거나 입력 스트림이 종료되어 `EOFError`가 발생하면 예외를 처리하여 Python traceback이 그대로 노출되며 비정상적으로 종료되는 것을 방지합니다.

사용자에게 상황과 종료 메시지를 안내한 후 프로그램을 종료합니다.

## 8-1. 백업 및 복구 전략

### state.json 백업 및 복구 전략

#### 1. 백업을 하는 이유

> 기존에는 `state.json`이 손상되면 기본 퀴즈 데이터로 초기화했기 때문에, 사용자가 추가한 퀴즈나 점수 기록을 잃을 수 있었습니다.

> 이를 방지하기 위해 정상 상태의 `state.json`을 `state.json.bak`으로 보관하고, 원본 파일이 손상된 경우 직전 정상 상태로 복구할 수 있도록 개선했습니다.

#### 2. 기존 대비 변경된 부분

> 기존에는 `state.json`을 바로 읽고 저장했지만, `JsonStateStore`에 백업 관련 기능을 추가했습니다.

```python
self.backup_file = f"{state_file}.bak"
```

주요 메서드는 다음과 같다.

```python
_load_file()       # JSON 파일 읽기 및 파싱
_create_backup()   # 정상 state.json을 .bak으로 백업
_restore_backup()  # 백업 파일 검증 및 원본 복구
```

> 저장 전에는 기존 `state.json`이 정상 JSON인지 확인한 후 백업합니다.

```python
self._create_backup()
```

#### 3. 개선 효과

* `state.json` 손상 시 사용자 데이터 유실 가능성 감소
* 직전 정상 상태로 자동 복구 가능
* 백업 파일까지 사용할 수 없을 때만 기본 데이터 사용
* 백업 책임을 `JsonStateStore` 내부에 두어 `QuizGame` 등 게임 로직의 변경을 최소화

#### 4. 전체 흐름 변화

기존 흐름:

```text
state.json 읽기
      ↓
정상 → 데이터 사용
손상 → 기본 데이터 사용
```

변경 후:

```text
[저장]

정상 state.json
      ↓
state.json.bak 생성
      ↓ (이후 사용자가 프로그램을 사용하면서 바뀐 최신 상태의 경우)
새 state.json 저장


[불러오기]

state.json 읽기
      ↓
정상 → 데이터 사용
      ↓ 손상
state.json.bak 확인
      ↓
정상 백업 → 백업에서 복구
      ↓ 백업 없음/손상
기본 데이터 사용
```

현재 백업은 여러 버전을 보관하지 않고 **직전 정상 상태 1개만 유지**하는 방식으로 구성했습니다.

## 11. JSON 기반 구조가 커지게 되면?

`state.json`은 **직접 CRUD를 수행하는 저장소라기보다, 프로그램 상태 전체를 저장하고 복원하는 영속성 파일**입니다. 실제 파일 접근은 `JsonStateStore`가 담당하고, 퀴즈 조작은 `QuizRepository`, 점수 조작은 `ScoreManager`, 전체 흐름 연결은 `QuizGame`이 맡고 있습니다.

### 기존 방식

- 프로그램 시작 시 `state.json` 전체를 읽어서 메모리에 올리고 파일을 읽기, 쓰기, 조회, 갱신, 추가, 삭제 작업 시 현재 상태 전체를 다시 저장합니다.

### 조회

```text
프로그램 실행
    ↓
QuizGame.load_state()
    ↓
JsonStateStore.load()
    ↓
state.json 전체 읽기
    ↓
quizzes / best_score / score_history 추출
    ↓
메모리 객체로 복원
```

- 프로그램 시작 시 `QuizGame.__init__()`에서 `load_state()`를 호출하고, 여기서 `JsonStateStore.load()`가 `state.json`을 읽습니다.

- `storage.py` 에서 파일 전체를 문자열로 읽은 다음 `json.loads()`로 파싱한 뒤 아래 3개의 값을 꺼내서 반환하고 이 3개의 값을 바탕으로 `Quiz` 객체로 만듭니다.

```text
quizzes
best_score
score_history
```

> 읽기는 `state.json` -> 메모리 전체 복원 방식

### 쓰기 

`QuizGame.save_state()`가 현재 메모리에 존재하는:

```text
전체 퀴즈
최고 점수
전체 점수 기록
```

을 가져와 `storage.save()`에 전달합니다.

`JsonStateStore.save()`에서는:

```python
{
    "quizzes": ...,
    "best_score": ...,
    "score_history": ...
}
```

형태의 데이터를 만든 다음 `"w"` 모드로 `state.json`을 열어 `json.dump()`로 저장합니다.

> **변경된 부분만 쓰는 것이 아니라 현재 상태 전체를 다시 저장한다는 것**

예를 들어 퀴즈 1개만 추가돼도:

```text
퀴즈 1개만 추가
     ↓
현재 퀴즈 전체 가져오기
현재 최고 점수 가져오기
현재 기록 전체 가져오기
     ↓
state.json 전체 다시 작성
```
이 됩니다.

---

### 조회(Read/Search)

> **퀴즈 목록을 볼 때마다 `state.json`을 다시 조회하는 구조가 아닙니다.**

프로그램 시작할 때 한 번 JSON을 읽어서:

```text
state.json
    ↓
QuizRepository.quizzes
ScoreManager.best_score
ScoreManager.score_history
```

처럼 메모리에 올려놓고 그 이후 조회는 **JSON 파일이 아니라 메모리에서 수행합니다.**

### 퀴즈 목록 조회

`show_quizzes()`는:

```python
self.repository.get_all()
```

을 사용해 현재 메모리에 있는 퀴즈 리스트를 가져옵니다.

### 퀴즈 개수 조회

```python
self.repository.get_count()
```

로 리스트 길이를 확인합니다.

### 최고 점수 조회

```python
self.score_manager.get_best_score()
```

로 메모리에 저장된 최고 점수를 가져옵니다.

### 기록 조회

```python
self.score_manager.get_score_history()
```

로 메모리의 기록 리스트를 조회합니다.

따라서 정확하게 말하면:

> `state.json`은 프로그램 시작 시 상태 복원에 사용되고, 프로그램 실행 중 일반적인 조회는 메모리에 복원된 객체를 대상으로 수행합니다.

---

### 추가(Create)

사용자가 새로운 퀴즈를 추가하면 먼저 `Quiz` 객체를 만듭니다.

그 다음:

```python
self.repository.add(new_quiz)
```

가 실행되고, `QuizRepository.add()`는 내부 리스트에 `append()`합니다. 

그 직후:

```python
self.save_state()
```

가 호출됩니다.

따라서 흐름은:

```text
사용자 퀴즈 입력
    ↓
Quiz 객체 생성
    ↓
QuizRepository 리스트에 append
    ↓
save_state()
    ↓
현재 전체 상태를 state.json에 다시 저장
```

이야.

즉 **state.json에 직접 한 줄을 추가하는 방식이 아닙니다.**

---

### 삭제(Delete)

사용자가 삭제할 번호를 입력하면:

```python
self.repository.delete(quiz_index)
```

를 호출하고 Repository에서는:

```python
self.quizzes.pop(quiz_index - 1)
```

으로 **메모리 리스트에서 먼저 삭제**합니다.

그 뒤:

```python
self.save_state()
```

를 호출합니다.

즉:

```text
삭제 번호 선택
    ↓
메모리 리스트에서 pop()
    ↓
save_state()
    ↓
삭제된 상태의 전체 데이터를
state.json에 다시 작성
```

따라서 JSON 내부에서 특정 퀴즈만 찾아서 지우는 것이 아닙니다.

---

### 갱신(Update)

갱신은 대표적으로 **최고 점수 갱신**이 있고

퀴즈가 끝나면:

```python
self.score_manager.update_best_score(score)
```

가 호출됩니다.

`ScoreManager`에서는 새 점수가 기존 최고 점수보다 높을 때:

```python
self.best_score = new_score
```

로 메모리 값을 변경합니다. 

또한 게임 기록도:

```python
self.score_history.append(...)
```

로 메모리에 추가됩니다.

그리고 게임이 끝나면:

```python
self.save_state()
```

가 호출됩니다.

따라서:

```text
게임 완료
   ↓
점수 계산
   ↓
best_score 메모리 값 갱신
   ↓
score_history 메모리에 기록 추가
   ↓
save_state()
   ↓
전체 state.json 다시 저장
```
---

###  표로 정리

| 동작 | 실제 처리 대상                | `state.json` 사용 방식       |
| -- | ----------------------- | ------------------------ |
| 읽기 | `JsonStateStore`        | 실행 시 파일 전체를 읽고 상태 복원     |
| 조회 | 메모리의 Repository/Manager | 실행 중에는 JSON을 다시 읽지 않음    |
| 추가 | 메모리 리스트                 | 추가 후 전체 JSON 다시 저장       |
| 삭제 | 메모리 리스트                 | 삭제 후 전체 JSON 다시 저장       |
| 갱신 | 메모리의 점수/기록              | 변경 후 전체 JSON 다시 저장       |
| 쓰기 | `JsonStateStore`        | 현재 상태 전체를 `"w"` 모드로 덮어쓰기 |

> **`state.json`은 매 작업마다 직접 검색, 수정하는 데이터베이스처럼 사용하지 않고, 프로그램 시작 시 전체 상태를 메모리로 복원하고 실행 중에는 메모리에서 조회, 추가, 삭제, 갱신한 뒤 상태가 변경될 때 전체 상태를 다시 JSON 파일에 저장하는 방식으로 사용하고 있습니다.**

즉, 데이터가 커지면 `1개 수정 → 전체 JSON 다시 저장`이라는 구조가 병목이 될 수 있습니다.

### 데이터가 증가한다면?

#### 1. 첫 번째 병목: JSON 전체 읽기

현재 방식은 

```text
state.json
   ↓ 전체 읽기
json.load()
   ↓
dict/list
   ↓
Quiz 객체 1000개 생성
```

- 퀴즈 한 문제만 필요하더라도 파일 전체를 읽어야 합니다.
- 1000개 중 한 문제만 찾고 싶어도
  - 퀴즈 1000개 전체 로드
  - 메모리에 저장
  - 원하는 문제 검색

을 해야 합니다.

> JSON 파일은 기본적으로 DB처럼 

```text
(특정 데이터)555번 데이터만 주세요
```
라고 요청할 수 없습니다.

> 데이터가 증가할수록 `초기 로딩 시간` 과 `메모리 사용량` 이 함께 증가합니다.

#### 2. 두 번째 병목: 전체 파일 다시 저장

문제 하나만 추가했다고 가정하면

```text
1000개 -> 1001개
```

가 되었을 뿐인데 실제로는 (현재 구조에서는)

```text
기존 1000개
+
새 문제 1개

↓ 전체 직렬화

1001개 전체를 state.json에 다시 작성
```

- 변경량은 1개인데 저장 작업은 전체 데이터 크기에 비례합니다.


#### 3. 세 번째 병목: 검색

현재 `Quiz` 가 `list`에 들어가 있는 구조인데 여기서

```python
quizzes = [
    quiz1,
    quiz2,
    quiz3,
    ...
]
```

- 특정 조건의 퀴즈만 찾으려면 처음부터 하나씩 확인해야 합니다.

```python
for quiz in quizzes:
    if quiz.question == target:
        ...
```

- 최악의 경우 시간복잡도를 표현하면

```text
O(n)
```

> 데이터가 커지면 `순차검색` 이 병목이 될 수 있습니다.

### 개선 방안 생각해보기

#### 1. 인덱싱

> 미션에서 배운 수준으로 적용해본다면 딕셔너리를 이용해서 인덱싱하는 방법을 생각해볼 수 있습니다.
> 인덱스는 데이터를 빠르게 찾기 위한 별도의 찾기표

- 딕셔너리를 활용해서 인덱싱을 한다면

```python
101 → Python 리스트 문제
102 → JSON 문제
103 → Git 문제
104 → 클래스 문제

quiz_index = {
    101: quiz1,
    102: quiz2,
    103: quiz3,
    104: quiz4
}

// 찾을 때
quiz_index[103]
```

- 굳이 전체 데이터를 다시 살펴보지 않아도 됨.
- 딕셔너리 조회는 `O(1)` 이라고 알려져있음

- 단점

> 인덱스를 만들면 검색 속도를 얻는 대신 메모리와 관리 비용이 듭니다.

원본이:

```text
quizzes
├─ Quiz A
├─ Quiz B
├─ Quiz C
└─ ...

인데 ID 인덱스까지 만들면:

quizzes
├─ Quiz A
├─ Quiz B
└─ ...

quiz_id_index
├─ 101 → Quiz A
├─ 102 → Quiz B
└─ 103 → Quiz C
```

> 원본 데이터 외에 추가적인 자료구조를 메모리에 유지해야 하니까 메모리 사용량은 증가합니다.

- 검색 성능은 좋아짐

리스트에서 ID를 찾는다면 일반적으로:

```text
O(n)
```

인데,

dictionary를 사용하면 평균적으로:

```text
O(1)
```

에 가까운 조회가 가능합니다.

예를 들어 100만 개 중 ID가 `738291`인 퀴즈를 찾는다고 한다면

리스트:

```text
quiz1
quiz2
quiz3
...
quiz738291 <- 발견 (순차 탐색)
```

반면 인덱스:

```python
quiz_index[738291]
```

처럼 바로 찾을 수 있습니다.

> **메모리를 조금 더 사용해서 검색 속도를 얻는다.** 라는 trade-off가 발생합니다.

---

- 데이터가 많아지면 인덱스도 많아지는 거 아닌가?

퀴즈가 100만 개라면 ID 인덱스에도 대략 100만 개의 항목이 필요합니다.

그래서:

```text
데이터 증가
   ↓
원본 데이터 메모리 증가
+
인덱스 메모리 증가
```

가 발생하며 또 하나의 비용이 있습니다.

> **데이터가 변경될 때 인덱스도 같이 관리해야 합니다**

퀴즈 추가:

```text
Quiz 추가
+
index 추가
```

퀴즈 삭제:

```text
Quiz 삭제
+
index 삭제
```

퀴즈의 인덱스 대상 값 변경:

```text
Quiz 수정
+
기존 index 수정
```

즉 검색은 빨라졌지만 **쓰기·추가·삭제의 관리 비용이 늘어날 수 있습니다.**

---

- 그럼 모든 속성에 인덱스를 만들면 되지 않을까?

> 하면 안 되는 이유는 관리 비용이 증가하기 때문입니다.

예를 들어 Quiz에:

```text
id
question
category
answer
hint
created_at
```

가 있다고 할 때 전부 인덱싱하면:

```text
ID index
question index
category index
answer index
hint index
created_at index
```

를 따로 관리해야 해야 합니다ㅏ.

그러면 검색은 다양하게 빨라질 수 있지만:

* 메모리 사용 증가
* 데이터 추가 비용 증가
* 삭제 비용 증가
* 수정 비용 증가
* 인덱스 자체 관리 비용 증가

라는 trade-off가 발생합니다.

> 그래서 실제 DB에서도 **모든 컬럼에 인덱스를 만들지 않습니다.**
> 주로 검색 조건으로 자주 사용하는 데이터에 만드는 것이 좋습니다.

예:

```sql
WHERE quiz_id = ?
WHERE category = ?
```

처럼 자주 찾는 필드는 인덱싱 가치가 높고, 거의 검색하지 않는 `hint` 같은 필드는 인덱스 가치가 낮을 수 있겠습니다.

> 현재 프로그램은 퀴즈를 리스트로 관리하기 때문에 별도의 검색 인덱스를 두고 있지 않습니다. 데이터가 많아지면 ID 등을 key로 하는 dictionary를 추가해 검색 속도를 높일 수 있습니다. 다만 인덱스도 데이터 수만큼 추가 정보를 유지해야 하므로 메모리를 더 사용하고, 데이터 추가, 삭제, 수정 시 인덱스도 함께 갱신해야 하는 비용이 발생합니다. 따라서 모든 데이터에 무조건 인덱스를 만드는 것이 아니라 **조회 빈도가 높고 검색에 자주 사용되는 기준에 선택적으로 인덱스를 만드는 것이 중요합니다.**

특히 **`인덱스 = 성능을 무조건 좋게 해주는 기능`이 아니라 `조회 성능과 저장 공간, 쓰기 비용의 교환`**이라는 `trade-off`이므로 적절하게 저울질을 해야 할 것 같습니다.


---

#### 2. 캐싱

> 자주 사용하는 결과를 빠른 저장공간에 미리 보관하는 것

- 예를 들어 퀴즈가 10만 개 있는데 사용자가 자주 "Python" 카테고리를 조회한다고 한다면

```text
10만 개 전체 검색
→ Python 문제 필터링
```

- 위 방법처럼 찾는 것이 아니라

```python
cache["python"] = [...]
```

- 이런 식으로 저장을 하고 난 뒤
- 두 번째 요청부터는 다시 전체 검색을 하지 않는 것

```text
첫 번째 요청

전체 데이터 검색
       ↓
Python 문제 결과 생성
       ↓
cache 저장


두 번째 요청

cache에서 바로 반환
```

#### 3. 데이터베이스 이용하기

```text
현재 JSON:

state.json 전체 읽기
↓
메모리 전체 로딩
↓
Python에서 검색
↓
전체 파일 저장
```

- DB로 바꾸면:

```text
SELECT 필요한 데이터
↓
DB가 인덱스를 이용해 검색
↓
필요한 행만 반환
```

- 그리고 문제 하나를 추가하면:

```sql
INSERT ...
```

- 문제 하나를 수정하면:

```sql
UPDATE ...
```

- 전체 데이터를 다시 파일에 작성할 필요가 없습니다.

#### JSON과 DB 비교해보면

- JSON

- 장점:
    - 구조가 단순함
    - 구현하기 쉬움
    - 사람이 직접 열어볼 수 있음
    - 작은 프로그램에 적합함
    - 별도의 DB 프로그램이 필요 없음

- 하지만 한계는:

```text
데이터 증가
 ↓
전체 로드 비용 증가
 ↓
메모리 사용 증가
 ↓
전체 저장 비용 증가
 ↓
검색도 직접 구현해야 함
```

- DB

- 반면 DB의 장점은:
    - 필요한 데이터만 조회 가능
    - 한 레코드만 추가/수정 가능
    - 인덱스를 이용한 빠른 검색 가능
    - 대용량 데이터를 모두 메모리에 올릴 필요가 없음

> 그래서 데이터 규모가 커질수록 데이터베이스를 이용하는 것이 좋다.

#### DB 도입을 고려한 객체지향 설계

- 저장 책임을 JsonStateStore로 분리했는데

```text
현재:

QuizGame
   ↓
JsonStateStore
   ↓
state.json
```

- 대규모 데이터 때문에 DB가 필요해지면 개념적으로:

```text
QuizGame
   ↓
DatabaseStateStore
   ↓
Database
```

와 같은 형태로 바꾸는 걸 생각할 수 있습니다.

> 그래서 저장 기능을 게임 진행 로직과 분리했습니다. 현재는 JSON을 사용하지만 데이터가 커져 DB가 필요해지면 저장 책임이 있는 부분을 중심으로 변경할 수 있도록 역할을 나눴습니다.

#### 결론

- 문제점
    - 현재 프로그램은 JSON 파일 전체를 메모리에 불러오고 상태가 변경되면 전체 데이터를 다시 저장하는 구조입니다.
    - 1000개 정도는 크게 문제가 되지 않을 수 있지만 데이터가 계속 증가하면 초기 로딩 시 파일 전체를 읽어야 하기 때문에 메모리 사용량과 로딩 시간이 증가합니다.
    - 또한 퀴즈 하나만 추가하거나 수정해도 전체 JSON을 다시 직렬화하여 저장하는 비용이 발생합니다.
    - 특정 퀴즈 검색도 리스트를 순차 탐색하면 데이터 수에 비례해 느려질 수 있습니다.

- 대안:

    - 검색이 자주 필요한 경우 ID나 카테고리를 key로 하는 dict 형태의 인덱스를 둘 수 있고, 반복적으로 조회하는 결과는 캐싱할 수 있습니다.
    - 데이터 규모가 더 커진다면 JSON 대신 DB를 사용하여 필요한 데이터만 조회하고 인덱스를 이용해 검색하며, 변경된 데이터만 `INSERT`, `UPDATE` 하는 방식이 더 적절합니다.

```text
1000개
→ 현재 JSON도 충분할 가능성이 높음

하지만
데이터가 계속 증가하고
검색/수정 빈도가 높아지고
부분 조회가 필요하다면

→ JSON 구조의 한계가 나타남
→ 인덱싱/캐싱 고려
→ 더 커지면 DB 고려
```
